Réplica NLP en severidad

Propósito

El pipeline de src/nlp_severity_app.py reproduce el estudio de ablación de NLP/Latex/main.tex con tres modelos:

  • M1: solo variables de flujo.
  • M2: solo embeddings narrativos.
  • M3: representación multimodal fusionada.

La entrada es run_paper_replication. El código añade controles de reproducibilidad que no aparecen en el manuscrito: tres rutas (frozen, raw, update_embeddings), reanudación por checkpoints, comparación estricta entre rutas y promoción condicionada de assets a LaTeX.

Protocolo bloqueado

Constantes como PAPER_PROTOCOL, PAPER_EXPECTED_COUNTS, PAPER_K_GRID y PAPER_VALIDATION_ALPHA fijan:

  • Target binario severity_target, holdout temporal con test_size=0.2, random_state=42.
  • Conteos esperados: 2.070 filas, 432 variables de flujo, 200 de embedding, 632 totales; split 1.656/414.
  • Grilla de \(k\) en modo manual: \( k\in\{10,15,20,25,30,40,50,70,100,150,200,250,300,350,400,432\} \).
  • Puntaje de validación \(\mathrm{Score}_{val} = \alpha F1_{global} + (1-\alpha)(1-\mathrm{FNRate})\) con \(\alpha=0.3\), \(\varepsilon=0.001\).
  • Folds CV interno/externo configurables (por defecto 5).

Etapas de ejecución

  1. Contexto: fingerprints del dataset congelado resultado.pkl, de la fuente raw, del Transformer fine-tuneado y del protocolo; se derivan a computed_run_id.
  2. Reanudar / cargar / comenzar: el código inspecciona Resultados/nlp_in_severity/paper_replication/<run_id>/. Si está completed, se carga el payload; si está running o failed, se retoma; si no existe checkpoint, se crea un manifest nuevo.
  3. Ruta congelada: carga resultado.pkl, normaliza columnas y ejecuta la validación contra las expectativas bloqueadas.
  4. Ruta raw: reconstruye desde eventos fuente, genera features de flujo, filtra por cobertura AVI, construye texto text_bert, resuelve el Transformer, extrae embeddings (método transformer_finetuned, max_length=128, batch=16, proyección cls), rankea dimensiones con RF y conserva las top-200 para ensamblar el dataset de 632 variables.
  5. Modalidades M1/M2/M3: para cada modelo se resuelven variables, se imputa por mediana, se rankea pre-SMOTE y se busca \(k\) con validación cruzada anidada; \(k^\ast\) se elige por mejor validation_score (desempate por el \(k\) más pequeño).
  6. Nested CV y ajuste final: folds externos e internos estratificados; SMOTE se aplica dentro de la búsqueda interna (sampling_strategy, k_neighbors), no directamente sobre el fold externo.
  7. Consolidación por ruta: tabla comparativa por modelo, métricas por clase, predicciones unificadas sobre los mismos IDs de test y la tabla de \(k\) para M3.
  8. Ruta update_embeddings (opcional): reemplaza columnas de embedding sobre el dataset congelado dejando flujo intacto.
  9. Comparación frozen/raw: cantidades discretas coinciden exactamente; métricas numéricas pueden diferir a lo sumo \(0.001\). Si la raw queda bloqueada o la comparación falla, toda la réplica queda blocked.
  10. Staging y promoción LaTeX: se generan accuracy_vs_k.png, f1_score_vs_k.png, false_negatives_pct_vs_k.png, validation_score_vs_k.png, metrics.png, gridsearch_k.tex y metricas_modelos.tex. La promoción sólo ocurre si la comparación aprueba.

Contraste con el manuscrito

  • El Transformer BERT en español no se reentrena en la reproducción; se reutiliza el último fine-tuneado compatible del registry.
  • La reducción se fija operacionalmente a top-200, no a una dimensión \(p\) genérica.
  • El ranking con RF se aplica por modalidad (uno por M1, M2 y M3) y sobre datos pre-SMOTE para evitar filtración.
  • El paper reporta la grilla de M3, pero el código busca \(k\) para las tres modalidades.
  • false_negative_rate_positive_class en _classification_metrics se calcula como \(\mathrm{FN}/N\) (no como \(\mathrm{FN}/P\)).
  • SMOTE se optimiza conjuntamente con XGBoost dentro de _paper_optimize_xgb_model, no como paso previo.
  • El holdout es temporal (split_mode="Temporal"); el estratificado queda como fallback.
  • La regla de \(k^\ast\) cambió a «mejor puntaje» en lugar de beneficio marginal.
  • Existen tres perfiles (Rápida, Amplia, GridSearch original) y dos backends.

Estructura de checkpoints y lectura

Bajo Resultados/nlp_in_severity/paper_replication/<run_id>/ conviven manifest.json, live_status.json, live_events.jsonl y los subdirectorios frozen/, raw_build/, raw/, update_emb_build/, update_emb/, compare/ y export/.

Al revisar una corrida el orden recomendado es: manifest.json → frozen/dataset_validation.json y raw/summary.json → compare/summary.json y compare/diff.csv → export/payload.json y los assets promovidos.

Réplica

El protocolo está bloqueado por constantes (PAPER_*) — cualquier cambio en seeds, splits o conteos invalida la corrida. Los fingerprints del dataset blindan la reproducibilidad.

Tres rutas. frozen (snapshot inmutable), raw (reconstruye desde fuente) y update_embeddings (re-extrae embeddings sobre flujo congelado).

SMOTE. Sólo dentro de la búsqueda interna del nested CV — nunca sobre el fold externo.
