Predicción de accidentes

Objetivo y fuentes

Construir y evaluar modelos que predigan la ocurrencia de un accidente en un pórtico, a partir de variables agregadas de flujo y, opcionalmente, variables derivadas de clusters de conductores. Los flujos se almacenan en DuckDB. Los accidentes provienen de archivos de eventos filtrados por tipo Accidente y Vía, con accidente_time y mapeo a pórticos cercanos vía Datos/Porticos.csv; el pórtico asignado queda como ultimo_portico.

Variables de clusters (opcional)

Si existe la tabla plate → cluster_label, se unen detecciones con su cluster \(\kappa\) y se agregan por \((p,\tau,\kappa)\). Se añade además la entropía \( H_{p,\tau}=-\sum_\kappa\mathrm{share}_{p,\tau,\kappa}\log\mathrm{share}_{p,\tau,\kappa} \). Se almacenan como cluster_share_*, cluster_flow_*, cluster_speed_*, etc.

Definición del target

Un accidente en \((t_a,p_a)\) se etiqueta en el intervalo anterior: \( \tau_a = \tau(t_a) - \Delta \), con

\[ y_{p,\tau} = \begin{cases} 1, & \text{si existe un accidente con }(p_a,\tau_a)=(p,\tau) \\ 0, & \text{en otro caso} \end{cases} \]
(2.4)
Variables
yp,τ
Target binario de "ocurrirá un accidente en el siguiente intervalo".
τa
Bin previo al accidente (lead-time de un Δ).
Implementación
src/drift_detection_app.py · _add_interval_accident_target

Así, \( y_{p,\tau}=1 \) significa «ocurrirá un accidente en el siguiente intervalo».

Partición, desbalance y modelos

Para evitar fuga temporal, el split es cronológico por interval_start: el tramo final es test (test_size). Dentro del bloque train/val se aísla validación con val_size. El desbalance se maneja con ponderación de clases (class_weight="balanced" en RF) o SMOTE aplicado solo sobre el entrenamiento (filas sintéticas marcadas como synthetic=True).

Se consideran tres familias: Random Forest, XGBoost y SVM (con StandardScaler y salida probabilística). Cada modelo produce un score \(s(x)\).

Calibración de umbral con FAR

\[ \mathrm{FAR}=\frac{FP}{FP+TN},\qquad \mathrm{Sens}=\frac{TP}{TP+FN} \]
(2.5)
Variables
FAR
False Alarm Rate — proporción de no-eventos clasificados como evento.
Sens
Sensibilidad / recall positivo.
Implementación
src/drift_detection_app.py · compute_classification_metrics
\[ \theta = \arg\max_{\theta:\mathrm{FAR}(\theta)\le \alpha}\mathrm{Sens}(\theta) \]
(2.6)
Variables
θ
Umbral óptimo sobre el score s(x).
α
Cota máxima admitida de FAR (configurable por experimento).
Implementación
src/drift_detection_app.py · youden_threshold

En test se reportan Accuracy, Precision, Recall, F1, FAR, Sens y ROC-AUC junto a la matriz de confusión.

Selección de features y Optuna

Un ranking de importancia con Random Forest ordena variables. Optuna optimiza hiperparámetros del modelo y de SMOTE: en cada trial se aplica SMOTE sobre train, se entrena, se calibra el umbral bajo la restricción de FAR en validación y se evalúa (p. ej. F1).

Efecto de clusters: Base vs. Base+Cluster

Para cuantificar el aporte de los clusters, se comparan dos escenarios sobre \(K=5,10,\dots\):

  • Base: top-\(K\) variables del ranking sin clusters.
  • Base+Cluster: top-\(K\) del ranking combinado.

Artefactos y XAI

El pipeline genera bajo Resultados/ CSV/DuckDB de features, datasets balanceados, resultados Optuna, experimentos iterativos y bundles reproducibles model_history/<run_id>/<strategy>/ con model.joblib, manifest.json, background.parquet y explain_rows.parquet.

Bundle reproducible

El manifest.json persiste modelo, hiperparámetros, columnas, métricas, umbral calibrado, split final, procedencia exacta de las flow features y de las variables de cluster, selección y si se usó balanceo. Con esto, la pestaña History reabre la explicación sin recalcular features.

La explicabilidad se calcula con SHAP sobre dos subconjuntos persistidos: hasta 128 filas reales de entrenamiento como background y hasta 64 filas de test enriquecidas con casos representativos (mayor score, TP fuerte, FP fuerte, FN relevante). Se reporta ranking global por \(\mathrm{mean}(|\mathrm{SHAP}|)\), agregación Base vs. Cluster, top específico de variables de cluster y casos locales. Los modelos de árbol usan TreeExplainer; SVM usa KernelExplainer sobre la probabilidad positiva.

FAR

El False Alarm Rate es la métrica operacional principal: cuántas alertas se emiten sin que ocurra un accidente. Un sistema de aviso en tiempo real exige FAR bajo aunque cueste sensibilidad.

Fuga temporal. Todos los splits se hacen por tiempo, nunca aleatorios — el modelo no debe ver el futuro.

SMOTE. Sólo sobre train. Las filas sintéticas se marcan con synthetic=True para auditarlas.
