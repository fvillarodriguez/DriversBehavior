Predicción de accidentes

Objetivo y contrato metodológico

El módulo de predicción de accidentes construye modelos supervisados que estiman, para cada pórtico \(p\) e intervalo temporal \(\tau\), la probabilidad de que ocurra un accidente en el siguiente intervalo. La unidad de decisión no es el vehículo individual, sino la celda agregada pórtico-tiempo. Esto permite transformar flujos vehiculares de alta frecuencia y, opcionalmente, perfiles de conducción derivados de clustering, en alertas operacionales evaluables por sensibilidad, falsas alarmas y costo.

La documentación LaTeX define el contrato científico del capítulo: fuentes de datos, discretización, ingeniería de variables, target con lead time de un intervalo, split temporal, desbalance, modelos, calibración, Optuna, experimentos y XAI. La documentación web conserva ese alcance y agrega las referencias de implementación reales que sostienen cada decisión.

Fuentes de datos y unidad observacional

Las detecciones vehiculares provienen de flujos, persistidos en DuckDB y consultados por rango temporal. Cada registro contiene, como mínimo, timestamp, pórtico, categoría vehicular, velocidad y, cuando se usan clusters, matrícula. Los accidentes provienen de archivos de eventos filtrados por tipo Accidente y vía expresa; su localización se asigna a pórticos cercanos usando Datos/Porticos.csv.

\[ r_j=(t_j,p_j,c_j,v_j,\mathrm{plate}_j),\qquad j=1,\dots,N. \]
(2.1)
Interpretación

Instante de detección.
\(p_j\)
Pórtico o estación AVI.
\(c_j\)
Categoría vehicular remapeada, por ejemplo liviano/pesado.
\(v_j\)
Velocidad observada.

Discretización temporal

El tiempo se discretiza en intervalos de tamaño \(\Delta\) minutos. Todas las variables supervisadas se calculan sobre la llave compuesta \((p,\tau)\), donde \(\tau\) es el inicio del intervalo. En la implementación, compute_flow_features usa dt.truncate(f"{interval_minutes}m"); compute_pm_features usa un índice entero equivalente en minutos.

\[ \tau(t)=\left\lfloor \frac{t}{\Delta}\right\rfloor \Delta. \]
(2.2)
Contrato

La granularidad \(\Delta\) debe ser la misma para features de flujo, features de cluster y target; de lo contrario se rompe la unión por (portico, interval_start).

Ingeniería de variables de flujo

Para cada pórtico \(p\), intervalo \(\tau\) y categoría \(c\), el pipeline calcula conteos, velocidades y transformaciones de tráfico. La versión usada por la app de predicción persiste columnas flow_*, speed_*, speed_std_*, density_*, delta_speed_* y delta_density_*. La implementación Polars de compute_pm_features añade además métricas robustas de distribución de velocidad: media, desviación estándar, armónica, mediana, cuartiles, IQR, MAD, coeficiente de variación, asimetría, curtosis, tasa de outliers, flujo total, proporción de pesados, densidad total, índice de congestión y vc_ratio.

\[ \begin{aligned} n_{p,\tau,c}&=\#\{j:p_j=p,\tau(t_j)=\tau,c_j=c\},\\ \overline v_{p,\tau,c}&=\frac{1}{n_{p,\tau,c}}\sum_{j:p_j=p,\tau(t_j)=\tau,c_j=c} v_j. \end{aligned} \]
(2.3)
Columnas
flow_count · speed_mean · speed_std
\[ \begin{aligned} q_{p,\tau,c}&=\frac{60}{\Delta}\frac{n_{p,\tau,c}}{L},\\ k_{p,\tau,c}&=\frac{q_{p,\tau,c}}{\overline v_{p,\tau,c}}. \end{aligned} \]
(2.4)
Variables
\(q\)
Flujo por hora normalizado por carriles.
\(k\)
Densidad macroscópica aproximada.
\(L\)
Número de carriles usado para normalización.
\[ \begin{aligned} \Delta \overline v_{p,\tau,c}&=\overline v_{p,\tau,c}-\overline v_{p,\tau-\Delta,c},\\ \Delta k_{p,\tau,c}&=k_{p,\tau,c}-k_{p,\tau-\Delta,c}. \end{aligned} \]
(2.5)
Uso

Las primeras diferencias codifican aceleraciones o degradaciones locales del régimen de tráfico y se calculan dentro de cada serie pórtico-categoría.

Variables agregadas de clusters

Cuando se dispone de una tabla plate → cluster_label, el sistema enlaza cada detección con el perfil conductual del vehículo y agrega por \((p,\tau,\kappa)\). En modo duro, la membresía es una etiqueta discreta. En modo suave, si el archivo contiene columnas cluster_prob_*, cada vehículo aporta parcialmente a todos los clusters según sus probabilidades posteriores; esto preserva información para conductores raros o asignaciones inciertas.

\[ \begin{aligned} n_{p,\tau,\kappa}&=\#\{j:p_j=p,\tau(t_j)=\tau,\hat c_j=\kappa\},\\ \mathrm{share}_{p,\tau,\kappa}&=\frac{n_{p,\tau,\kappa}}{\sum_{\kappa'}n_{p,\tau,\kappa'}}. \end{aligned} \]
(2.6)
Modo duro
cluster_label · cluster_share_* · cluster_flow_*
\[ \begin{aligned} w_{p,\tau,\kappa}&=\sum_{j:p_j=p,\tau(t_j)=\tau} r_{j,\kappa},\\ \mathrm{share}_{p,\tau,\kappa}&=\frac{w_{p,\tau,\kappa}}{N_{p,\tau}},\\ \overline v_{p,\tau,\kappa}^{\,soft}&=\frac{\sum_j r_{j,\kappa}v_j}{\sum_j r_{j,\kappa}}. \end{aligned} \]
(2.7)
Modo suave

compute_cluster_features detecta cluster_prob_*, transforma a formato largo y suma pesos de membresía.

\[ H_{p,\tau}=-\sum_{\kappa}\mathrm{share}_{p,\tau,\kappa}\log(\mathrm{share}_{p,\tau,\kappa}). \]
(2.8)
Interpretación

La entropía mide la mezcla conductual del intervalo: valores altos indican coexistencia de varios perfiles de conducción.

Definición del target con lead time

El target no marca el mismo intervalo del accidente, sino el intervalo inmediatamente anterior. Esta decisión impone una semántica predictiva: \(y_{p,\tau}=1\) significa que la celda \((p,\tau)\) antecede a un accidente en el próximo intervalo. En código, add_accident_target aplica floor(interval_minutes) a accidente_time y resta \(\Delta\).

\[ \tau_a=\tau(t_a)-\Delta. \]
(2.9)
Lead time

Si el accidente ocurre en el intervalo \(\tau(t_a)\), el ejemplo positivo usado para entrenar es \(\tau(t_a)-\Delta\).

\[ y_{p,\tau}= \begin{cases} 1, & \text{si existe un accidente con }(p_a,\tau_a)=(p,\tau),\\ 0, & \text{en caso contrario}. \end{cases} \]
(2.10)
Contrato

La unión se hace por portico e interval_start. Accidentes sin pórtico asignado se excluyen antes de construir el target.

Construcción del dataset y split temporal

El dataset final contiene una fila por \((p,\tau)\), variables numéricas y target. Primero se calculan variables macro de flujo; luego, si hay clusters, se unen por (portico, interval_start); finalmente se agrega el target. Para evitar fuga temporal, el split se ordena por interval_start; el bloque final se reserva para test y, en el protocolo conservador, el bloque previo de entrenamiento se divide otra vez para validación.

\[ \begin{aligned} \mathcal{D}_{train}&=\{(x_i,y_i):t_i\lt T_{val}\},\\ \mathcal{D}_{val}&=\{(x_i,y_i):T_{val}\le t_i\lt T_{test}\},\\ \mathcal{D}_{test}&=\{(x_i,y_i):t_i\ge T_{test}\}. \end{aligned} \]
(2.11)
Invariante

La validación y el test contienen sólo filas reales; las filas sintéticas de SMOTE, cuando existen, permanecen en entrenamiento.

Desbalance de clases

La ocurrencia de accidentes es rara. La app soporta tres modos de entrenamiento: sin balance interno, ponderación de clases y SMOTE interno. La ponderación usa class_weight="balanced" para Random Forest/SVM, scale_pos_weight automático para XGBoost y pos_weight para la red neuronal. SMOTE se aplica únicamente dentro del conjunto de entrenamiento o fold temporal, nunca sobre validación ni test. Los datasets balanceados legacy de la pestaña Balance marcan filas con synthetic=True para impedir doble SMOTE.

Regla antileakage

La calibración del umbral debe ver únicamente scores de validación/OOF reales. Si un dataset trae filas sintéticas, split_train_val_for_threshold separa validación desde filas reales y concatena sintéticos sólo al train final.

Scores, calibración y umbral operacional

Cada modelo produce un score \(s(x)\). Antes de escoger el umbral, el score puede calibrarse con tres métodos: sin calibración, Platt scaling sigmoid o isotonic regression. En SVM, si la orientación del score invierte la clase positiva, orient_scores_for_objective lo multiplica por \(-1\) antes de calibrar.

\[ \begin{aligned} s_i&=f_\theta(x_i),\\ \tilde s_i&=g(s_i),\qquad g\in\{\mathrm{id},\sigma(a s+b),g_{\mathrm{iso}}\}. \end{aligned} \]
(2.12)
Implementación
fit_score_calibrator · ScoreCalibrator · orient_scores_for_objective
\[ \mathrm{FAR}=\frac{FP}{FP+TN},\qquad \mathrm{Sens}=\frac{TP}{TP+FN}. \]
(2.13)
Métrica operacional

FAR mide falsas alarmas entre no-eventos; sensibilidad mide captura de accidentes.

\[ \theta^\star=\arg\max_{\theta:\mathrm{FAR}(\theta)\le\alpha}\mathrm{Sens}(\theta),\qquad \hat y_i=\mathbf{1}[\tilde s_i\ge\theta^\star]. \]
(2.14)
Función
select_threshold_for_metric · select_threshold_for_far

Además de FAR, el selector de umbral admite F1, Balanced F1, MCC, Recall@N alertas/día y costo operacional. PR-AUC y ROC-AUC son métricas de ranking; cuando se usan como criterio de threshold, el umbral operativo permanece en 0.5 porque no definen por sí mismas un punto de corte.

\[ \begin{aligned} F1&=\frac{2TP}{2TP+FP+FN},\\ \mathrm{MCC}&=\frac{TP\,TN-FP\,FN}{\sqrt{(TP+FP)(TP+FN)(TN+FP)(TN+FN)}}. \end{aligned} \]
(2.15)
Catálogo

THRESHOLD_OBJECTIVE_LABELS y OPTUNA_OBJECTIVE_LABELS separan el objetivo de umbral del objetivo de búsqueda.

\[ \begin{aligned} \mathrm{alerts/day}&=\frac{TP+FP}{\mathrm{days}},\\ \mathrm{cost}&=c_{FN}FN+c_{FP}FP. \end{aligned} \]
(2.16)
Operación

Permite comparar modelos bajo presupuesto de alertas o costo asimétrico entre no detectar y sobredetectar.

Protocolos de evaluación

El protocolo conservador entrena en train, ajusta calibrador y umbral en validation, y evalúa una sola vez en test. El protocolo robusto une train+validation, genera scores OOF con folds temporales, calibra score y threshold sobre OOF, reentrena con todo train+validation y evalúa en test.

\[ \begin{aligned} \mathcal{S}_{OOF}&=\{(y_i,\tilde s_i): i\in V_m,\ m=1,\dots,M\},\\ \theta^\star&=\operatorname{SelectThreshold}(\mathcal{S}_{OOF}),\\ f^\star&=\operatorname{Fit}(\mathcal{D}_{train}\cup\mathcal{D}_{val}). \end{aligned} \]
(2.17)
Fallback

Si no hay folds temporales válidos con dos clases, el código cae al protocolo conservador y deja nota en el resultado.

Métricas de evaluación

En test se reportan accuracy, precision, recall, sensibilidad, especificidad, FAR, ROC-AUC, PR-AUC, Brier score, F1, Balanced F1, F1 por clase, MCC, falsos negativos, falsos positivos, verdaderos positivos, verdaderos negativos, soporte positivo, captura de positivos, tasa de FN, alertas por día, falsas alarmas por día, recall aproximado por evento, costo operacional, costo por día, recall bajo presupuesto de alertas y matriz de confusión.

Pestaña Optuna

La pestaña Optuna usa la selección activa de variables y crea tres configuraciones: Base, Cluster y Base + Cluster. Para cada configuración ejecuta variantes sin balance interno y, si imbalanced-learn está disponible, variantes con SMOTE. La búsqueda usa TPESampler, poda opcional con MedianPruner, n_jobs para trials paralelos y controles separados para paralelismo interno de Random Forest/XGBoost.

Optuna puede ajustar hiperparámetros de Random Forest, Balanced Random Forest, XGBoost, SVM y Neural Network; también puede optimizar top_k, usando ranking calculado sobre train real por Random Forest o mutual information. La métrica objetivo de Optuna se escoge de un catálogo que incluye f1, roc_auc, pr_auc, balanced_f1, mcc, brier_score, recall_at_alerts_per_day, operational_cost y variantes multiobjetivo Pareto en los experimentos de calibración.

Separación de objetivos

El objetivo de Optuna selecciona hiperparámetros y, opcionalmente, número de variables. El objetivo de threshold selecciona el punto de corte operacional. Esta separación evita confundir un buen ranking PR-AUC/ROC-AUC con un umbral operativo aceptable.

Los resultados se persisten en Resultados/optuna_*.json y Resultados/optuna_*trials.csv. El JSON mantiene dataset_fingerprint, variables seleccionadas, feature_cols, search_space, optuna_settings y resultados agrupados por modelo, by_balance_mode y by_calibration_method. La vista canónica en memoria es optuna_results_store; _get_active_optuna_best() prefiere SMOTE cuando existe y respeta la calibración activa.

Pestaña Modelos

La pestaña Modelos entrena Base, Cluster y Base + Cluster con parámetros independientes. Antes de ejecutar, _apply_optuna_model_params_to_state(...) intenta aplicar los mejores hiperparámetros de Optuna a cada grupo. El match exige mismo modelo, mismo modo de balance y misma calibración, salvo que el usuario habilite fallback de calibración. Si el origen de variables es un batch Optuna explícito, Modelos puede reentrenar todas las subcorridas reales del batch, preservando trazabilidad.

Al finalizar se muestran métricas por protocolo, deltas contra Base, matrices de confusión, curvas de entrenamiento cuando existen y se registra la corrida en Resultados/experiment_history.jsonl y Resultados/model_history/. La estrategia Base + Cluster puede persistir bundle XAI reproducible.

XAI para Base + Cluster

Cuando termina la estrategia Base + Cluster, el sistema puede guardar un bundle reproducible bajo Resultados/model_history/. El manifest.json registra modelo, hiperparámetros, columnas, métricas, umbral calibrado, split final, procedencia de features de flujo, procedencia exacta de features de cluster, selección de variables y balance usado. Esto permite que la pestaña History reabra la explicación sin recalcular features ni recargar manualmente archivos de clusters.

\[ \begin{aligned} I_j&=\frac{1}{m}\sum_{i=1}^{m}|\phi_{ij}|,\\ C_g&=\frac{\sum_{j\in g}I_j}{\sum_{\ell}I_\ell},\qquad g\in\{\mathrm{Base},\mathrm{Cluster}\}. \end{aligned} \]
(2.18)
SHAP

\(I_j\) es importancia global por variable y \(C_g\) cuantifica la proporción explicativa atribuible a variables Base o Cluster.

El bundle persiste hasta 128 filas reales de entrenamiento como background y hasta 64 filas de test para explicar, enriquecidas con casos representativos: mayor score, verdadero positivo fuerte, falso positivo fuerte y falso negativo relevante. Random Forest y XGBoost usan TreeExplainer; SVM y otros modelos usan KernelExplainer sobre la salida probabilística positiva. Si SHAP falla o la corrida es antigua, la UI informa que XAI no está disponible sin invalidar el resto del historial.

Lectura científica

El valor académico de la comparación Base vs. Base + Cluster depende de tres invariantes: mismo split temporal, mismo objetivo de threshold y misma política de balance. Si esos invariantes cambian, la diferencia de métricas deja de aislar el aporte de los clusters.

Riesgos metodológicos controlados

El pipeline controla fuga temporal con splits cronológicos, evita SMOTE fuera de train, separa ranking de threshold y guarda fingerprints de dataset para no reutilizar Optuna sobre datos incompatibles. Los principales riesgos residuales son baja cantidad de positivos por tramo, sensibilidad del lead time a \(\Delta\), y dependencia de la calidad del mapeo accidente-pórtico.
