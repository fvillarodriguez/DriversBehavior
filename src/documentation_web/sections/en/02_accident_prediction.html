Accident prediction

Objective and methodological contract

The accident-prediction module builds supervised models that estimate, for each gantry \(p\) and temporal interval \(\tau\), the probability that an accident will occur in the next interval. The decision unit is not an individual vehicle, but the aggregated gantry-time cell. This turns high-frequency vehicle detections and, optionally, clustering-derived driver profiles into operational alerts evaluated by sensitivity, false alarms, and cost.

The LaTeX documentation defines the scientific contract of the chapter: data sources, discretization, feature engineering, one-interval lead-time target, temporal split, imbalance, models, calibration, Optuna, experiments, and XAI. The web documentation preserves that scope and adds the implementation references that support each decision.

Data sources and observation unit

Vehicle detections come from flujos, persisted in DuckDB and queried by time range. Each record contains at least timestamp, gantry, vehicle category, speed, and, when clusters are used, license plate. Accidents come from event files filtered by type Accident and expressway; their location is assigned to nearby gantries using Datos/Porticos.csv.

\[ r_j=(t_j,p_j,c_j,v_j,\mathrm{plate}_j),\qquad j=1,\dots,N. \]
(2.1)

\(c_j\)

\(v_j\)

Temporal discretization

Time is discretized into intervals of size \(\Delta\) minutes. All supervised variables are computed over the composite key \((p,\tau)\), where \(\tau\) is the interval start. In implementation, compute_flow_features uses dt.truncate(f"{interval_minutes}m"); compute_pm_features uses an equivalent integer minute index.

\[ \tau(t)=\left\lfloor \frac{t}{\Delta}\right\rfloor \Delta. \]
(2.2)
Contract

The granularity \(\Delta\) must be identical for flow features, cluster features, and target; otherwise the join by (portico, interval_start) is invalid.

Flow feature engineering

For each gantry \(p\), interval \(\tau\), and category \(c\), the pipeline computes counts, speeds, and traffic transformations. The app-level implementation persists flow_*, speed_*, speed_std_*, density_*, delta_speed_*, and delta_density_*. The Polars implementation in compute_pm_features also adds robust speed-distribution metrics: mean, standard deviation, harmonic speed, median, quartiles, IQR, MAD, coefficient of variation, skewness, kurtosis, outlier rate, total flow, heavy-vehicle proportion, total density, congestion index, and vc_ratio.

\[ \begin{aligned} n_{p,\tau,c}&=\#\{j:p_j=p,\tau(t_j)=\tau,c_j=c\},\\ \overline v_{p,\tau,c}&=\frac{1}{n_{p,\tau,c}}\sum_{j:p_j=p,\tau(t_j)=\tau,c_j=c} v_j. \end{aligned} \]
(2.3)

Aggregated cluster variables

When a plate → cluster_label table is available, the system joins each detection with the vehicle's behavioural profile and aggregates by \((p,\tau,\kappa)\). In hard mode, membership is a discrete label. In soft mode, if the file contains cluster_prob_* columns, each vehicle contributes partially to all clusters according to posterior probabilities; this preserves information for rare drivers or uncertain assignments.

\[ \begin{aligned} n_{p,\tau,\kappa}&=\#\{j:p_j=p,\tau(t_j)=\tau,\hat c_j=\kappa\},\\ \mathrm{share}_{p,\tau,\kappa}&=\frac{n_{p,\tau,\kappa}}{\sum_{\kappa'}n_{p,\tau,\kappa'}}. \end{aligned} \]
(2.6)
Hard mode
cluster_label · cluster_share_* · cluster_flow_*
\[ \begin{aligned} w_{p,\tau,\kappa}&=\sum_{j:p_j=p,\tau(t_j)=\tau} r_{j,\kappa},\\ \mathrm{share}_{p,\tau,\kappa}&=\frac{w_{p,\tau,\kappa}}{N_{p,\tau}},\\ \overline v_{p,\tau,\kappa}^{\,soft}&=\frac{\sum_j r_{j,\kappa}v_j}{\sum_j r_{j,\kappa}}. \end{aligned} \]
(2.7)
Soft mode

compute_cluster_features detects cluster_prob_*, melts to long format, and sums membership weights.

\[ H_{p,\tau}=-\sum_{\kappa}\mathrm{share}_{p,\tau,\kappa}\log(\mathrm{share}_{p,\tau,\kappa}). \]
(2.8)
Interpretation

Entropy measures behavioural mixing within an interval: high values indicate coexistence of several driving profiles.

Target definition with lead time

The target does not mark the accident interval itself, but the immediately preceding interval. This imposes a predictive semantics: \(y_{p,\tau}=1\) means that cell \((p,\tau)\) precedes an accident in the next interval. In code, add_accident_target floors accidente_time to interval_minutes and subtracts \(\Delta\).

\[ \tau_a=\tau(t_a)-\Delta. \]
(2.9)
Lead time

If the accident happens in interval \(\tau(t_a)\), the positive training example is \(\tau(t_a)-\Delta\).

\[ y_{p,\tau}= \begin{cases} 1, & \text{if there exists an accident with }(p_a,\tau_a)=(p,\tau),\\ 0, & \text{otherwise}. \end{cases} \]
(2.10)
Contract

The join is performed by portico and interval_start. Accidents without assigned gantry are excluded before target construction.

Dataset construction and temporal split

The final dataset contains one row per \((p,\tau)\), numerical variables, and target. First, macro flow variables are computed; then, if clusters exist, they are joined by (portico, interval_start); finally, the target is added. To avoid temporal leakage, the split is ordered by interval_start; the final block is reserved for test and, in the conservative protocol, the preceding training block is split again for validation.

\[ \begin{aligned} \mathcal{D}_{train}&=\{(x_i,y_i):t_i\lt T_{val}\},\\ \mathcal{D}_{val}&=\{(x_i,y_i):T_{val}\le t_i\lt T_{test}\},\\ \mathcal{D}_{test}&=\{(x_i,y_i):t_i\ge T_{test}\}. \end{aligned} \]
(2.11)
Invariant

Validation and test contain only real rows; synthetic SMOTE rows, when present, stay in training.

Class imbalance

Accident occurrence is rare. The app supports three training modes: no internal balancing, class weighting, and internal SMOTE. Weighting uses class_weight="balanced" for Random Forest/SVM, automatic scale_pos_weight for XGBoost, and pos_weight for the neural network. SMOTE is applied only inside the training set or temporal fold, never on validation or test. Legacy balanced datasets from the Balance tab mark rows with synthetic=True to prevent double SMOTE.

Anti-leakage rule

Threshold calibration must see only real validation/OOF scores. If a dataset contains synthetic rows, split_train_val_for_threshold separates validation from real rows and concatenates synthetic rows only into the final train block.

Scores, calibration, and operational threshold

Each model produces a score \(s(x)\). Before selecting the threshold, the score can be calibrated with three methods: no calibration, Platt sigmoid scaling, or isotonic regression. For SVM, if score orientation reverses the positive class, orient_scores_for_objective multiplies it by \(-1\) before calibration.

\[ \begin{aligned} s_i&=f_\theta(x_i),\\ \tilde s_i&=g(s_i),\qquad g\in\{\mathrm{id},\sigma(a s+b),g_{\mathrm{iso}}\}. \end{aligned} \]
(2.12)
Implementation
fit_score_calibrator · ScoreCalibrator · orient_scores_for_objective
\[ \mathrm{FAR}=\frac{FP}{FP+TN},\qquad \mathrm{Sens}=\frac{TP}{TP+FN}. \]
(2.13)
Operational metric

FAR measures false alerts among non-events; sensitivity measures accident capture.

\[ \theta^\star=\arg\max_{\theta:\mathrm{FAR}(\theta)\le\alpha}\mathrm{Sens}(\theta),\qquad \hat y_i=\mathbf{1}[\tilde s_i\ge\theta^\star]. \]
(2.14)
Function
select_threshold_for_metric · select_threshold_for_far

Besides FAR, the threshold selector supports F1, Balanced F1, MCC, Recall@N alerts/day, and operational cost. PR-AUC and ROC-AUC are ranking metrics; when they are used as the threshold criterion, the operational threshold remains 0.5 because they do not define a cutoff by themselves.

\[ \begin{aligned} F1&=\frac{2TP}{2TP+FP+FN},\\ \mathrm{MCC}&=\frac{TP\,TN-FP\,FN}{\sqrt{(TP+FP)(TP+FN)(TN+FP)(TN+FN)}}. \end{aligned} \]
(2.15)
Catalog

THRESHOLD_OBJECTIVE_LABELS and OPTUNA_OBJECTIVE_LABELS separate the threshold objective from the search objective.

\[ \begin{aligned} \mathrm{alerts/day}&=\frac{TP+FP}{\mathrm{days}},\\ \mathrm{cost}&=c_{FN}FN+c_{FP}FP. \end{aligned} \]
(2.16)
Operation

This supports model comparison under an alert budget or asymmetric cost between missed and excess detections.

Evaluation protocols

The conservative protocol trains on train, fits score calibrator and threshold on validation, and evaluates once on test. The robust protocol merges train+validation, generates OOF scores with temporal folds, calibrates score and threshold on OOF, retrains on all train+validation, and evaluates on test.

\[ \begin{aligned} \mathcal{S}_{OOF}&=\{(y_i,\tilde s_i): i\in V_m,\ m=1,\dots,M\},\\ \theta^\star&=\operatorname{SelectThreshold}(\mathcal{S}_{OOF}),\\ f^\star&=\operatorname{Fit}(\mathcal{D}_{train}\cup\mathcal{D}_{val}). \end{aligned} \]
(2.17)
Fallback

If no valid temporal folds with two classes exist, the code falls back to the conservative protocol and records a note in the result.

Evaluation metrics

On test, the system reports accuracy, precision, recall, sensitivity, specificity, FAR, ROC-AUC, PR-AUC, Brier score, F1, Balanced F1, class-wise F1, MCC, false negatives, false positives, true positives, true negatives, positive support, positive capture, FN rate, alerts per day, false alarms per day, approximate event recall, operational cost, cost per day, recall under alert budget, and the confusion matrix.

Optuna tab

The Optuna tab uses the active feature selection and creates three configurations: Base, Cluster, and Base + Cluster. For each configuration, it runs variants without internal balancing and, when imbalanced-learn is available, variants with SMOTE. Search uses TPESampler, optional MedianPruner pruning, n_jobs for parallel trials, and separate controls for Random Forest/XGBoost internal parallelism.

Optuna can tune Random Forest, Balanced Random Forest, XGBoost, SVM, and Neural Network hyperparameters; it can also optimize top_k, using a ranking computed on real train data by Random Forest or mutual information. The Optuna objective metric is chosen from a catalog that includes f1, roc_auc, pr_auc, balanced_f1, mcc, brier_score, recall_at_alerts_per_day, operational_cost, and Pareto multiobjective variants in calibration experiments.

Objective separation

The Optuna objective selects hyperparameters and, optionally, the number of variables. The threshold objective selects the operational cutoff. This separation avoids confusing good PR-AUC/ROC-AUC ranking with an acceptable operational threshold.

Results are persisted in Resultados/optuna_*.json and Resultados/optuna_*trials.csv. The JSON stores dataset_fingerprint, selected variables, feature_cols, search_space, optuna_settings, and results grouped by model, by_balance_mode, and by_calibration_method. The canonical in-memory view is optuna_results_store; _get_active_optuna_best() prefers SMOTE when available and respects the active calibration.

Models tab

The Models tab trains Base, Cluster, and Base + Cluster with independent parameters. Before execution, _apply_optuna_model_params_to_state(...) attempts to apply the best Optuna hyperparameters to each group. The match requires the same model, balance mode, and calibration, unless the user enables calibration fallback. If the feature source is an explicit Optuna batch, Models can retrain all real subruns from the batch while preserving traceability.

At completion, the tab shows metrics by protocol, deltas against Base, confusion matrices, training curves when available, and records the run in Resultados/experiment_history.jsonl and Resultados/model_history/. The Base + Cluster strategy can persist a reproducible XAI bundle.

Experiments tab

The Experiments tab supports execution, review, and import of experiments. New modes cover feature sampling, sample-size search, best highway segment, optimal segment + \(K\) mix, score + threshold calibration, and controlled comparison over a frozen temporal split. Experiments use checkpoints, live SQLite databases, and ZIP export/import so long runs can be paused, resumed, and audited.

XAI for Base + Cluster

When the Base + Cluster strategy finishes, the system can save a reproducible bundle under Resultados/model_history/. The manifest.json records model, hyperparameters, columns, metrics, calibrated threshold, final split, flow-feature provenance, exact cluster-feature provenance, variable selection, and balance mode. This lets the History tab reopen the explanation without recomputing features or manually reloading cluster files.

\[ \begin{aligned} I_j&=\frac{1}{m}\sum_{i=1}^{m}|\phi_{ij}|,\\ C_g&=\frac{\sum_{j\in g}I_j}{\sum_{\ell}I_\ell},\qquad g\in\{\mathrm{Base},\mathrm{Cluster}\}. \end{aligned} \]
(2.18)
SHAP

\(I_j\) is global feature importance and \(C_g\) quantifies the explanatory share attributed to Base or Cluster variables.

The bundle persists up to 128 real training rows as background and up to 64 test rows for explanation, enriched with representative cases: highest score, strong true positive, strong false positive, and relevant false negative. Random Forest and XGBoost use TreeExplainer; SVM and other models use KernelExplainer over positive-class probability. If SHAP fails or the run predates the bundle format, the UI reports XAI as unavailable without invalidating the rest of the history.

Scientific reading

The academic value of the Base vs. Base + Cluster comparison depends on three invariants: same temporal split, same threshold objective, and same balance policy. If those invariants change, metric differences no longer isolate the contribution of clusters.

Controlled methodological risks

The pipeline controls temporal leakage with chronological splits, prevents SMOTE outside train, separates ranking from threshold, and stores dataset fingerprints so Optuna is not reused on incompatible data. Main residual risks are low positive counts by segment, lead-time sensitivity to \(\Delta\), and dependence on accident-to-gantry mapping quality.

Governing principle

The model does not predict “historical accidents”; it predicts risk in the interval preceding the accident. Lead-time semantics are the center of the chapter.
