Chapter · Multimodal replication

NLP on severity replication

Purpose

The pipeline in src/nlp_severity_app.py reproduces the ablation study from NLP/Latex/main.tex with three models:

  • M1: flow variables only.
  • M2: narrative embeddings only.
  • M3: fused multimodal representation.

The entry point is run_paper_replication. The code adds reproducibility controls absent from the manuscript: three paths (frozen, raw, update_embeddings), checkpoint resume, strict comparison between paths, and conditional asset promotion to LaTeX.

Locked protocol

Constants such as PAPER_PROTOCOL, PAPER_EXPECTED_COUNTS, PAPER_K_GRID and PAPER_VALIDATION_ALPHA fix:

  • Binary target severity_target, temporal holdout with test_size=0.2, random_state=42.
  • Expected counts: 2,070 rows, 432 flow variables, 200 embedding variables, 632 total; split 1,656/414.
  • \(k\) grid in manual mode: \( k\in\{10,15,20,25,30,40,50,70,100,150,200,250,300,350,400,432\} \).
  • Validation score \(\mathrm{Score}_{val} = \alpha F1_{global} + (1-\alpha)(1-\mathrm{FNRate})\) with \(\alpha=0.3\), \(\varepsilon=0.001\).
  • Inner/outer CV folds configurable (5 by default).

Execution stages

  1. Context: fingerprints of the frozen dataset resultado.pkl, the raw source, the fine-tuned Transformer and the protocol; derived into computed_run_id.
  2. Resume / load / start: the code inspects Resultados/nlp_in_severity/paper_replication/<run_id>/. If completed, the payload is loaded; if running or failed, it resumes; if no checkpoint, a fresh manifest is created.
  3. Frozen path: loads resultado.pkl, normalises columns and validates against locked expectations.
  4. Raw path: rebuilds from source events, generates flow features, filters by AVI coverage, builds text_bert, resolves the Transformer, extracts embeddings (method transformer_finetuned, max_length=128, batch=16, projection cls), ranks dimensions with RF and keeps the top-200 to assemble the 632-variable dataset.
  5. Modalities M1/M2/M3: per model, variables are resolved, median-imputed, ranked pre-SMOTE and \(k\) is searched with nested CV; \(k^\ast\) is chosen by best validation_score (ties broken by smallest \(k\)).
  6. Nested CV and final fit: stratified outer/inner folds; SMOTE is applied inside the inner search (sampling_strategy, k_neighbors), not directly on the outer fold.
  7. Per-path consolidation: comparative table per model, per-class metrics, unified predictions over the same test IDs and the \(k\) table for M3.
  8. update_embeddings path (optional): replaces embedding columns on the frozen dataset leaving flow intact.
  9. frozen/raw comparison: discrete quantities must match exactly; numeric metrics may differ by at most \(0.001\). If raw is blocked or the comparison fails, the whole replication is blocked.
  10. Staging and LaTeX promotion: accuracy_vs_k.png, f1_score_vs_k.png, false_negatives_pct_vs_k.png, validation_score_vs_k.png, metrics.png, gridsearch_k.tex and metricas_modelos.tex are produced. Promotion only happens if the comparison passes.

Regularisation (min_child_weight, gamma, reg_alpha, reg_lambda) is only included when use_regularization is on. Backend can be gridsearch (GridSearchCV) or optuna (24 trials by default).

Contrast with the manuscript

  • The Spanish BERT Transformer is not retrained in the replication; the latest compatible fine-tune is reused from the registry.
  • Reduction is fixed operationally to top-200, not a generic \(p\).
  • RF ranking is applied per modality (one for M1, M2 and M3) over pre-SMOTE data to avoid leakage.
  • The paper reports the M3 grid, but the code searches \(k\) for all three modalities.
  • false_negative_rate_positive_class in _classification_metrics is computed as \(\mathrm{FN}/N\) (not \(\mathrm{FN}/P\)).
  • SMOTE is jointly optimised with XGBoost inside _paper_optimize_xgb_model, not as a previous step.
  • The holdout is temporal (split_mode="Temporal"); stratified is the fallback.
  • The \(k^\ast\) rule changed to "best score" instead of marginal benefit.
  • Three profiles exist (Fast, Wide, Original GridSearch) and two backends.

Checkpoint structure and reading order

Under Resultados/nlp_in_severity/paper_replication/<run_id>/ live manifest.json, live_status.json, live_events.jsonl and the subdirectories frozen/, raw_build/, raw/, update_emb_build/, update_emb/, compare/ and export/.

When auditing a run the recommended order is: manifest.json → frozen/dataset_validation.json and raw/summary.json → compare/summary.json and compare/diff.csv → export/payload.json and the promoted assets.
