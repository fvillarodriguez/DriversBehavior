MA-AIRL operating manual

What this UI does

The Reward Learning page learns policies and rewards that explain expert trajectories generated by SUMO. The active implementation requires real \(s,a,s'\) transitions from consecutive FCD samples; it does not train MA-AIRL on AVI or on the former \(s'=s\) fallback. The flow lives in src/multi_agent_rl_app.py, the core in src/marl_core.py, and FCD reconstruction in src/SUMO.py::build_sumo_fcd_transition_dataset.

Configuration flow

  1. Expert trajectories from SUMO FCD. Set .sumocfg, tripinfo.xml, sumo_fcd.xml, and the FCD period. Ejecutar SUMO y construir transiciones FCD calls sumo/sumo-gui with --fcd-output and --fcd-output.acceleration true. Importar FCD existente parses an existing FCD XML directly.
  2. State features. After transitions are reconstructed, the UI lists state_*, flow_context_*, and vms_active columns. Defaults come from DEFAULT_STATE_COLS: speed, lane, headway, relative speed, flow context, and VMS.
  3. Optional clusters. Resultados/cluster_*.csv files are useful for analysis or policy names; they do not replace expert FCD.
  4. SUMO parameters. Duration, step, GUI, and emission strategy support runs and route generation, but they do not change an imported FCD dataset.
  5. AVI and gantry diagnostics. Reconstructs partial AVI transitions for inspection. The UI explicitly separates them from MA-AIRL training.
  6. Shared policies. Configuration is derived from agent_id; the user can adjust policy count and names before training/export.
Input contract

is_sumo_fcd_transition_dataset requires source="sumo_fcd". If transitions are empty, come from AVI, or lack that provenance, the MA-AIRL training button rejects the run.

Expert dataset

build_sumo_fcd_transition_dataset iterates through FCD XML with iterparse, sorts samples by vehicle and time, and forms one transition from every consecutive pair. The resulting table contains identifiers (trajectory_id, agent_id), state/next-state columns (state_speed_kmh, next_speed_kmh, lane, position, coordinates, headway), flow context, and observed actions (action_delta_speed_kmh, action_accel_m_s2, action_lane_change).

MA-AIRL training

In MA-AIRL (SUMO FCD), the UI uses temporal_split == "train" when present, instantiates MAIRLManager, and runs train_step(batch_size) for the selected iterations. Controls are Iteraciones, Batch size, \(\gamma\), LR Policy, LR Reward, Hidden units, and Device; auto resolves cuda, mps, or cpu.

Implementation
src/marl_core.py · MAIRLAgent.f · MAIRLManager.train_step

For each agent_id, the manager creates a Gaussian policy \(q_\theta(a\mid s)\), a reward network \(g_\omega(s,a)\), and a potential \(h_\phi(s)\). Each iteration samples expert transitions and policy actions, updates reward/potential with the adversarial loss, then updates the policy with the shaped reward.

Metrics and export

The UI stores disc_loss, policy_loss, reward_mean, agents, and transitions in st.session_state["mairl_metrics_log"]. The Exportar perfiles MA-AIRL button writes simulación/mairl_policy_profiles.json with feature_cols, action_cols, and de-normalized policy_actions evaluated at each policy's mean state.

Current limitations

  • The fidelity of \(s'\) and observed actions depends on the FCD period; the UI default is 1 second.
  • Headway and relative speed are estimated within FCD by time, edge, lane, and position.
  • AVI is diagnostic, not a MA-AIRL training source.
  • CEM (legacy) remains available as a heuristic comparison, not as the main MA-AIRL flow.
